# 클라우드에 올려서 모두가 쓰기

## 결론
- **Firebase Hosting에는 올릴 수 없다.** Firebase Hosting은 정적 파일(HTML·JS) 전용이고 이 앱은 파이썬 서버(Streamlit)가 돌아야 한다. Firebase App Hosting도 Node(Next.js·Angular) 전용이다.
- **대안: 같은 Google 프로젝트의 Cloud Run + Cloud Storage.** Firebase Blaze와 같은 '쓴 만큼 내는' 요금이고, 요청이 없으면 인스턴스가 0으로 줄어 비용이 거의 나오지 않는다. 이력(SQLite)은 **Litestream**으로 Cloud Storage에 실시간 복제해, 컨테이너가 꺼졌다 켜져도 그대로 복원된다. 코드(`db.py`) 수정 없이 해결된다.
- 준비한 것: `Dockerfile`(Litestream 포함), `start_cloud.sh`(복원 → 복제하며 실행), `litestream.yml`, `deploy_cloudrun.sh`(버킷 생성·권한·배포 한 번에). 복제→삭제→복원 주기는 앱의 DB 코드로 검증했다(2026-10-07). 실제 Cloud Run 배포는 결제 프로젝트가 필요해 사용자 계정에서 처음 한 번 실행해야 한다 [확인 필요].

## 비용 (대략, 2026-10 기준 공개 요금표 — 실제 청구는 콘솔 확인 [확인 필요])
| 항목 | 무료 범위 | 이 앱 예상 |
|---|---|---|
| Cloud Run (요청 기반 과금, min-instances 0) | 월 요청 200만 건, vCPU 18만 초, 메모리 36만 GiB초 | 하루 몇 명이 몇십 분 쓰는 수준이면 무료 범위 안. 넘어도 월 1~2천 원대 |
| Cloud Storage (이력 복제본) | 5GB·월 | 이력 DB는 수 MB → 사실상 0 |
| Cloud Build (배포 때 이미지 빌드) | 하루 120분 | 배포 1회 3~5분 → 0 |
| Anthropic API | — | 접속자 각자 키(세션) 또는 공통 키. 호출량만큼 |

`--min-instances 1`(항상 켜 둠)로 바꾸면 첫 접속이 빨라지는 대신 월 1만 원 안팎이 나온다. 기본은 0.

## 동작 방식
1. 접속이 오면 Cloud Run이 컨테이너를 켠다(첫 접속 10~20초). `start_cloud.sh`가 Cloud Storage의 복제본에서 `history.db`를 복원한다.
2. Litestream이 Streamlit을 자식으로 띄우고, DB 변경을 1초 간격으로 Cloud Storage에 복제한다.
3. 한동안 접속이 없으면 컨테이너가 꺼진다. 다음 접속 때 1부터 반복. 이력은 유지된다.
4. 인스턴스는 **최대 1개**로 고정한다(SQLite는 한 곳에서만 써야 함). 부서 단위 동시 접속 수십 명까지는 1개로 충분하다.

## gcloud CLI 설치와 로그인(Windows, 한 번만)
1. https://cloud.google.com/sdk/docs/install 에서 **Windows용 설치 파일(GoogleCloudSDKInstaller.exe)** 을 받아 실행. 선택지는 기본값으로 두고 설치. 마지막 화면의 "Start Google Cloud SDK Shell"과 "Run gcloud init" 체크는 그대로 두어도 되고, 끄고 아래처럼 직접 해도 된다.
2. 시작 메뉴에서 **Google Cloud SDK Shell**(또는 PowerShell)을 열고 입력:
   ```
   gcloud auth login
   ```
   브라우저가 열리면 Google Cloud 프로젝트(Firebase 프로젝트)의 소유자 계정으로 로그인하고 "허용". 창에 "You are now logged in"이 뜨면 끝.
3. 프로젝트 ID 확인: Firebase 콘솔 → 프로젝트 설정 → "프로젝트 ID"(표시 이름이 아니라 소문자·하이픈으로 된 ID). 또는 `gcloud projects list`.
4. (선택) 기본 프로젝트 지정: `gcloud config set project 내-프로젝트-id`. 배포 스크립트가 어차피 지정하므로 생략 가능.

## 올리는 순서
1. Google Cloud 콘솔에서 프로젝트 선택(Firebase 프로젝트 그대로 써도 됨), 결제 연결 확인.
2. PC에 [gcloud CLI](https://cloud.google.com/sdk/docs/install) 설치 → `gcloud auth login`.
3. 앱 폴더에서 실행. Windows PowerShell:
   ```
   cd 앱폴더경로
   .\deploy_cloudrun.ps1 -Project 내-프로젝트-id -AppPassword 접속암호
   ```
   맥·리눅스·Git Bash:
   ```
   PROJECT=내-프로젝트-id REGION=asia-northeast3 APP_PASSWORD=접속암호 ./deploy_cloudrun.sh
   ```
   PowerShell에서 "스크립트 실행이 비활성화" 오류가 나면 먼저 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.
   3~6분 뒤 접속 URL이 출력된다. 처음에는 Cloud Run·Cloud Build 권한 동의 창이 뜰 수 있다.
4. URL 접속 → 접속 비밀번호 → 설정 → AI 연결에 각자 키. 운영자가 공통 키를 쓰게 하려면 `ANTHROPIC_API_KEY=... ./deploy_cloudrun.sh`.
5. 코드가 바뀌면 `.\update_cloud.ps1 -Project 내-프로젝트-id` 한 줄(git pull → 빌드 → 배포, 3~5분). 비밀번호·키는 기존 값이 유지되고, 이력은 버킷에 남아 그대로 이어진다. 배포 중에도 기존 버전이 계속 서비스되며 새 버전이 뜨면 자동으로 바뀐다.
6. 내리기: `gcloud run services delete ebs-request-agent --region asia-northeast3`. 복제본(`gs://<프로젝트>-ebs-history`)은 남으니 다시 올리면 복원된다.

## 보안 — 외부 URL로 열 때
- `APP_PASSWORD`를 반드시 둔다(없으면 URL만 알면 누구나 들어옴). 비밀번호 하나를 부서가 공유하는 방식이라 실사용 인증은 아니다. 사람별 로그인이 필요하면 Cloud Run 앞에 IAP(Identity-Aware Proxy, Google 계정 로그인)를 두는 것이 다음 단계다.
- 국감 요구자료·내부 수치가 Google Cloud(서울 리전)에 저장된다. 사내 보안 규정상 허용되는지 먼저 확인 [확인 필요]. 버킷은 공개 접근 차단·균일 권한으로 만들어진다.
- API 키는 접속자 브라우저 세션에만 보관(서버 저장 없음). 공통 키를 환경변수에 두는 경우 접속자 전원이 그 키로 호출한다.
- 업로드한 파일 원본은 저장하지 않고 추출한 값만 DB에 들어간다(기존과 같음).

## 다른 선택지와 비교
| 방법 | 비용 | 이력 보존 | 비고 |
|---|---|---|---|
| **Cloud Run + Litestream→GCS (권장)** | 거의 0 | 유지 | 코드 수정 없음. 인스턴스 1개 고정 |
| Cloud Run + Cloud SQL(PostgreSQL) | 월 1만 원 이상(DB 상시) | 유지 | `db.py` SQL 전환 작업 필요(하루 안팎) |
| Streamlit Community Cloud | 0 | 재시작 시 소실 | 외부 서비스에 코드·데이터. 시연용 |
| Render·Railway·Fly.io | 무료~월 1만 원 | 디스크 추가 시 유지 | Dockerfile 그대로 사용 가능 |
| 사내 공용 PC `run_server.bat` | 0 | 유지 | 사내망 밖에서 접속 불가, PC가 켜져 있어야 함 |

## 알려진 한계
- 첫 접속(콜드 스타트) 10~20초. 자주 쓰는 시간대가 정해져 있으면 `--min-instances 1`로 바꿔 없앨 수 있다.
- 세션 상태(입력 중인 내용, 세션에 넣은 키)는 컨테이너가 꺼지면 사라진다. DB에 저장한 것은 유지된다.
- 큰 파일(HWP 수십 MB) 업로드는 메모리 1Gi 기준 문제없으나, 더 크면 `--memory 2Gi`.

## 실제 배포에서 겪은 문제와 해결(2026-10-07, 새 프로젝트 ebs-test-a2c4e)
| 증상 | 원인 | 해결(스크립트에 반영됨) |
|---|---|---|
| PowerShell이 `gs://… not found: 404`에서 멈춤 | gcloud가 안내문을 stderr로 내보내는데 PowerShell 'Stop' 모드가 오류로 취급 | 종료 코드로 판단, 버킷은 list로 확인 |
| `Container import failed` 반복 | `gcloud run deploy --source`(빌드+배포 한 번에)가 새 프로젝트에서 실패 | 빌드(`gcloud builds submit`)와 배포(`--image`)를 분리, Cloud Run 서비스 에이전트에 Artifact Registry 읽기 권한 |
| `failed to load /app/start_cloud.sh: no such file or directory` | Windows git이 `.sh`를 CRLF로 받아 `#!/bin/sh\r` 해석기를 찾음 | Dockerfile에서 `sed -i 's/\r$//'`, `.gitattributes`로 `*.sh`·`*.yml`·Dockerfile LF 고정 |
| PowerShell 창이 저절로 닫힘 | 탐색기에서 .ps1을 더블클릭 실행 | PowerShell을 먼저 열고 그 안에서 실행 |
| 한글 깨짐(`?꾨줈?앺듃`) | Windows PowerShell 5.1이 BOM 없는 UTF-8 스크립트를 cp949로 읽음 + 콘솔 코드페이지 | `.ps1`에 UTF-8 BOM과 `[Console]::OutputEncoding = UTF8` 추가, `.bat`에 `chcp 65001`(스크립트에 반영됨). 그래도 깨지면 `chcp 65001` 후 실행 |
| 중간중간 빨간 글씨 | gcloud·pip가 진행 상황·안내를 stderr로 내보내고 PowerShell이 stderr를 빨갛게 표시 | 오류가 아님. 스크립트는 종료 코드로 판단하며 진짜 실패면 마지막에 `실패:`로 끝남 |

첫 성공 배포: 2026-10-07, 리비전 00007. 접속 URL은 `…run.app` 두 형태 모두 유효(결정적 URL과 기본 URL).
