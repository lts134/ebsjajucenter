# 보안 점검서 — 2026-10-08

## 요약
- 점검 범위: `app/` 전체(코드·배포 스크립트·컨테이너·설정). 코드를 직접 읽는 정적 점검 + 별도 독립 점검(같은 날, 읽기 전용)의 결과를 합쳤다. 외부 침투 테스트는 하지 않았다.
- 결과: **높음 2건·중간 8건·낮음 10건**을 찾았고, 그중 코드로 막을 수 있는 **16건은 이번에 반영**했다. 나머지 4건은 운영자 설정(비밀 저장소·접속 통제·서비스 계정)과 구조적 한계로, 아래 "운영자가 할 일"과 "남은 한계"에 적었다.
- 전제: 이 앱은 센터별 집계값과 대외 공문 초안을 다루며, 외부 URL(Cloud Run)에 비밀번호 하나로 열려 있다. 개인 단위 원자료는 올리지 않는 것이 운영 원칙이다(운영 매뉴얼 7).

## 점검 기준
1. 비밀값(접속 비밀번호·API 키·복제 자격증명)이 코드·이미지·로그·화면에 남지 않는가
2. 접속자가 서버를 거쳐 다른 것(내부망·파일 시스템·다른 접속자의 키)에 닿을 수 없는가
3. 외부 문서(요구서·첨부)가 앱의 동작을 바꿀 수 없는가(주입·압축 폭탄·외부 요청 유발)
4. 기록(DB·회신 파일·백업)이 사라지거나 다른 계정에 읽히지 않는가
5. 다른 서버·클라우드로 옮겨도 같은 보호가 유지되는가

## 확인했고 문제가 없던 것
- SQL은 전부 바인딩. 동적 표 이름은 `sqlite_master`에서 얻은 값만.
- `unsafe_allow_html` 14곳의 외부 문자열은 모두 `ui.esc`, 미리보기 `st.html`은 `html.escape`. 채팅 답변은 `safe_md`.
- 비밀번호 비교는 `hmac.compare_digest`, 실패 로그에 비밀번호 없음. 설정 화면의 키는 브라우저 세션 메모리에만 있고 호출 기록·보고서·오류문에 키가 들어가지 않음. 공용 키는 주소 변경 차단.
- 요구서 원문·도구 결과·초안 프롬프트는 `pii.redact` 경유, 값 행은 모델에 보내지 않음.
- XML 파서는 엔티티 확장 보호(expat 2.6), 외부 엔티티 없음. zip은 디스크에 풀지 않음. 파일명은 `safe_filename`.
- subprocess는 고정 인자·셸 미사용. XSRF 보호 켜짐. 버킷은 공개 차단·균일 권한. 복제 복원 실패 시 앱이 뜨지 않음(fail-closed).

## 운영자가 할 일(코드 밖)
1. **비밀값을 Secret Manager로**(Cloud Run): 
   ```
   echo -n '<비밀번호>' | gcloud secrets create app-password --data-file=-
   echo -n '<키>' | gcloud secrets create anthropic-key --data-file=-
   gcloud run services update ebs-request-agent --region asia-northeast3 --set-secrets APP_PASSWORD=app-password:latest,ANTHROPIC_API_KEY=anthropic-key:latest --remove-env-vars APP_PASSWORD,ANTHROPIC_API_KEY
   ```
   이후 `update_cloud.ps1`을 돌릴 때 `-AppPassword`를 주지 않으면 비밀 연결이 유지된다 [확인 필요: 첫 적용 때 콘솔에서 환경변수 탭 확인].
2. **접속 통제 한 단계 더**: 회사 Google Workspace가 있으면 Cloud Run 앞에 **IAP(Identity-Aware Proxy)** 를 두고 `--no-allow-unauthenticated`로 바꾼다. 그러면 비밀번호 하나가 아니라 사내 계정으로 로그인하며, 누가 접속했는지 남는다. 사내 서버면 SSO 리버스 프록시(oauth2-proxy 등).
3. **전용 서비스 계정**: `gcloud iam service-accounts create ebs-run` → 버킷에 `roles/storage.objectAdmin`만 → `gcloud run services update … --service-account ebs-run@<프로젝트>.iam.gserviceaccount.com`.
4. **관리자 비밀번호 분리**: `APP_ADMIN_PASSWORD`를 따로 두면 백업·복원·전체 삭제는 관리자만 할 수 있다.
5. **하루 AI 상한**: `LLM_DAILY_BUDGET_USD=20` 정도로 시작(공용 키일 때 특히). 넘으면 그날은 규칙 기반으로 동작한다.
6. **배포 시간**: 사용자가 없는 시간에 배포하고, 직후 설정 → 백업·초기화의 기록 건수를 확인한다.
7. **통합 대시보드 저장 파일**(.html)의 '계정정보' 영역에 평문 비밀번호가 들어 있다. 앱은 읽지 않지만, 파일이 공유된 적이 있으면 해당 계정 비밀번호를 바꾼다.
8. **백업 파일 취급**: 내려받은 `.db`는 기록 전체(요구서 원문·담당자 이름 포함)다. 암호화된 사내 저장소에만 두고 메일·메신저로 보내지 않는다. 서버 안 사본은 10개만 남는다(`APP_BACKUP_KEEP`).
9. **의존성 점검**: 분기마다 `pip install pip-audit && pip-audit -r requirements.txt` [확인 필요: 사내 보안 지침의 주기].
10. **키 순환**: 공용 API 키는 담당자 변경·유출 의심 시 즉시 재발급. 설정 화면의 '키 지우기'는 세션 키만 지운다.

## 남은 한계(이번 범위 밖)
- 사용자 식별이 없다: 사이드바 이름은 자유 입력이라 승인 기록의 이름을 믿으려면 IAP/SSO가 필요하다(위 2).
- 요구서 속 사람 이름은 가리지 않는다(`pii.py`는 전화·이메일·주민번호·계좌 등 패턴만). 이름 패턴 검출은 오탐이 많아 넣지 않았다. 의원실 보좌관 이름 등이 원문에 있으면 모델로 전송된다 — 원문 올리기 전 지우는 것이 원칙.
- 프롬프트 주입은 규칙으로 줄였을 뿐 완전히 막지 못한다. 기록을 바꾸는 도구는 현재 건의 항목·사유·초안에 한정되고 삭제·승인은 사람만 한다.
- SQLite 1인스턴스 구조라 무중단 이중화는 없다(`docs/배포_호환성.md` 6).
- 호스트 이름이 내부 IP로 풀리는 경우(DNS)는 `check_base_url`이 잡지 못한다. 사내 게이트웨이는 서버 환경변수로만 두는 것이 원칙.
